# 在线化就绪度评估：从离线单帧到连续视频流

> 回答两个问题：(1) 现在离「在线 3D 实例感知 + 语义地图构建」还有多远；
> (2) 从离线单帧升级到连续视频流上的在线感知与时序融合，具体要补什么。
>
> 结论：**算法骨架已经是因果的，缺的是编排、实时性和位姿。真正的分水岭是 SLAM。**

---

## 0. 一句话结论

现在的状态是 **「因果算法 + 离线编排 + 数据集 GT 位姿」**。

- 检测→分割→3D 提升**确实逐帧在线跑**（进程内循环，模型只加载一次）；
- 跨帧关联算法**本身严格因果**（只看历史滑动窗口，不看未来帧）；
- 但**关联与融合在序列末尾统一批处理**，实例语义嵌入和 3D 实例点云都是**事后重放**出来的；
- **位姿 100% 来自数据集 `traj.txt`**，代码库里没有任何里程计 / 闭环 / 位姿图。

所以严格讲：现在跑的是「按帧顺序处理离线数据」，不是「连续视频流上的在线感知」。
差距不在算法思路，而在工程编排 + 实时性 + 位姿自给。

## 0.5 Demo A 到底要什么：三种定义，三种距离

上一版评估容易让人误解成「Demo A 还早」。其实取决于 Demo A 怎么定义——
**这三种定义的距离差着一个数量级**，必须分开谈：

| Demo A 的定义 | 还需要什么 | 距离 | 备注 |
|---|---|---|---|
| **A1 效果演示**：语义地图 + 文本查询 + 第一视角视频，用标准 RGB-D 序列（GT 位姿） | 已基本具备，剩下是**换场景 + 打磨观感** | **几天** | 社区通行做法：OVI-MAP / ConceptFusion 一类工作也用 GT 位姿，**没有 SLAM 不等于不合格** |
| **A2 真在线增量演示**：边跑边建图、边查询，第 t 帧只依赖 0..t，增量结果≈批聚合 | **S1 编排改造**（仍是 GT 位姿） | **1–2 周** | 算法已是因果的，纯粹是把调用挪进逐帧循环 + 嵌入/点云改增量 |
| **A3 自给位姿的真机在线**：不依赖任何 GT 轨迹，自己估位姿 + 闭环 | **S3 接 SLAM** 及其后的判据重调 | **1–2 月** | 这才是「上真机」的门槛，但**未必属于 Demo A 的必需要求** |

**关键纠正**：真正让现在这版 Demo A 站不住的，**不是"在线"，是"质量"**——
AP@0.50 只有 0.240（office_0 那段）/ 0.519（8 场景宏平均），掩码边缘肉眼可见不准。
S1 只需 1–2 周就能解决"在线"的名义问题；掩码质量才是要花大力气的地方，
且换检测器已验证无效（§5.5），得动分割器。

**建议路径**：先做 A1→A2（几天 + 1–2 周），让 Demo A 名副其实；
S3 单列，按是否需要上真机再决定投入。对标论文普遍止步于 A2。

## 1. 时序融合的四级划分：我们在 L1，目标是 L3

| 级别 | 能力 | 状态 | 证据 |
|---|---|---|---|
| **L0** | 单帧独立检测+分割，帧间无身份 | 早已超过 | — |
| **L1** | 跨帧关联，同一物体有稳定全局 ID | **已达成（质量中等）** | 单轨率 0.706、纯轨率 0.887、碎片率 1.363、标签一致 0.984 |
| **L2** | 多观测**融合**：把 N 次观测合成一个更准的 3D 实例 + 更鲁棒的语义 | **部分达成，但是离线的** | 实例点云靠 `replay_instance_fusion` 事后重放；CLIP 嵌入靠 `extract_instance_embeddings` 遍历全序列后面积加权平均 |
| **L3** | **在线增量融合** + 闭环后轨道合并 + 地图老化 | 未开始 | 无闭环；已分裂的两条轨道不会在线合并 |

碎片率 1.363 说明：同一物体平均被切成 1.36 条轨道。L1 做到了「大部分时候 ID 稳定」，
但还没做到「一条轨道 = 一个物体」。

## 2. 已经真正在线的部分（不用重写）

| 组件 | 位置 | 在线性 |
|---|---|---|
| 逐帧 检测→SAM2→3D 提升 | `tools/run_sequence_efficient.py` | ✅ 进程内循环，模型只加载一次（旧版逐帧 spawn 子进程 30.7s/帧，90% 是脚手架开销，已修） |
| 因果跨帧关联 | `src/mapping/geometric_instance_tracker.py` | ✅ `update(obs, frame_index)`；体素滑动窗口 `voxel_window_size=20`；`last_processed_frame` 保护；**不使用未来帧** |
| 单帧内过分割合并 | `merge_frame_instances()` | ✅ 用体素覆盖率在**当前帧内**合并重复观测，并重新做 3D 提升 |
| 增量体素地图 | `src/mapping/online_voxel_map.py` | ✅ `update()` 增量写入，`to_numpy()` 按需导出 |

关联判据从 IoU 换成**体素覆盖率**是关键改进：同一物体覆盖率 ~0.7+、不同物体 ~0，间隔干净，
修掉了「视角变化导致质心漂移把同一物体切成两条轨道」的老问题。

## 3. 假在线：目前仍是离线批处理的部分

| 环节 | 现状 | 为什么不算在线 |
|---|---|---|
| **跨帧关联** | 序列末尾统一跑一次 | `run_sequence_efficient` 文档明写「关联 / 预览 / 融合只在末尾对整条序列跑一次」。算法因果 ≠ 编排在线 |
| **实例 CLIP 嵌入** | 遍历全序列收集裁剪图 → 批量编码 → **面积加权平均** → L2 归一化 | 必须等所有帧跑完才能算出实例语义，无法「边走边查」 |
| **实例 3D 融合** | `replay_instance_fusion` 按已有记录重放 | 事后脚本，明确声明「不重新推理、不估计位姿」 |
| **评估** | `evaluate_against_gt` 序列末尾批量跑 | 不影响在线性，但说明整条链路是批处理思维 |

## 4. 根本性缺口（这才是"多远"的尺子）

### 4.1 位姿完全依赖数据集 GT —— 最大缺口

```python
# src/datasets/replica_sequence.py
self.pose_path = self.scene_directory / "traj.txt"
self.camera_to_world = load_camera_poses(self.pose_path)
```

全库检索 `loop_closure` / `pose_graph` / `relocal` / `odometry` / `slam` / `ORB` / `ICP`
**零命中**（"nice-slam" 只是数据集来源标记，不是我们实现了 SLAM）。

这不只是"少个模块"：关联判据（体素覆盖率）**直接依赖位姿精度**。
位姿一漂，同一物体的跨帧体素重合度就塌，覆盖率判据失效，碎片率会显著恶化。
我们目前报的 0.706 单轨率是**在 GT 位姿下的上界**，真实 SLAM 位姿下必然更低。

### 4.2 实时性差约 6 倍

| 场景 | 均值 | P95 | FPS | 检测占比 |
|---|---|---|---|---|
| office_0 | 191.1 ms | 238.7 | 5.23 | 132.6 ms |
| office_1 | 156.0 ms | 199.6 | 6.41 | 130.4 ms |
| office_3 | 218.1 ms | 254.1 | 4.58 | 128.8 ms |

检测占 ~70%。按 30fps 视频流算，实时率仅 **0.17×**。
且这是 RTX 3090；Demo B 目标平台 RK3588 另算。

### 4.3 没有检测/跟踪分工

每帧都完整跑一遍 Grounding DINO（130ms）。在线系统的常规做法是
**低频检测 + 高频传播**（每 N 帧检测一次，中间帧用光流/掩码 warp/SAM2 传播），
这一层目前完全没有。

### 4.4 无闭环、无地图边界管理

- 已分裂的两条轨道不会在线合并（离线 `plan_merges` 只在单帧内合并）；
- 体素地图只增不减，长时间运行内存/算力单调增长；
- 无实例重识别（物体离开视野再回来会被判为新实例）。

## 5. 分期路线与工作量估计

| 阶段 | 内容 | 难度 | 估计 | 依赖 |
|---|---|---|---|---|
| **S1：把因果算法接成真在线** | tracker.update 挪进逐帧循环；CLIP 嵌入改增量 running average；实例点云增量累积；暴露「当前已发现实例」查询接口 | 低（算法现成，改编排） | **1–2 周** | 无 |
| **S2：追实时** | 检测降频 + SAM2 掩码传播；检测/分割异步流水线；目标 10–15 fps | 中（工程优化） | **2–4 周** | S1 |
| **S3：接 SLAM** | 接入 ORB-SLAM3 / Nice-SLAM 提供位姿；重测位姿误差对覆盖率判据的冲击；必要时放宽门限/改用鲁棒判据 | **高（最大不确定性）** | **1–2 月** | S1 |
| **S4：长时序鲁棒** | 闭环后轨道合并、地图老化/遗忘、实例重识别 | 高 | 1–2 月 | S3 |

**分水岭是 S3**。S1/S2 只是把已有的东西接对、跑快；
S3 决定这套东西能不能离开数据集、上真机。在 S3 完成前，
任何「在线」指标都是在 GT 轨迹上测的乐观值。

## 6. 建议的验收口径

现在说"在线"容易被质疑，建议改用可验证的三个数字说话：

1. **实时率**：`处理帧率 / 采集帧率`（当前 0.17×，目标 ≥1.0×）；
2. **因果性**：断言第 t 帧的输出只依赖 0..t 帧（tracker 已满足，编排需改造）；
3. **在线一致性**：在线增量算出的实例嵌入 / 点云，与离线批聚合结果的偏差
   （余弦 / Chamfer），用来证明"增量 ≈ 全量"。

没有这三条，所谓"在线感知"只是把离线数据按帧顺序喂进去。
